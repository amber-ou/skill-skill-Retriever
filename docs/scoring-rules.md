# 評分規則（Scoring Rules）

版本：`scoring-rules@1.1.0`（本文件變更即需遞增版本號；已存在的分數需標註產生時的規則版本，規則版本改變不強制回溯重算，但下次查核時應以新版重新評估）

## `recommendation_status` 授權不明確的一致性規則（1.1.0 新增）

**可信度分數與「授權是否已釐清」是兩件不同的事，前者不能替代後者。** 可信度分數是五個
子項（授權明確性／來源可追溯／維護狀態／內容行為一致／無可疑指令）的加權合計，其他四項
表現再好，都不代表授權條款本身已經釐清。

**分類規則（決定 `recommendation_status`，不影響可信度分數本身）**：只要符合以下任一情況，
`recommendation_status` 一律標示 **「需人工確認」**，且必須在備註中標明原因為「授權」，
不論可信度分數是多少：

1. Repo 內完全找不到 LICENSE／LICENSE.txt 等正式授權檔案。
2. 僅在 README、徽章圖片、`package.json` 的 `license` 欄位等**次要位置聲稱**某授權（如
   「MIT」），但沒有對應的正式授權檔案落實這個聲稱。
3. 內容明確衍生自外部來源，而該來源本身的授權狀態不明或未附著。

只有當 repo 內**確實存在**正式的 LICENSE／LICENSE.txt 檔案（且其授權條款與宣稱的授權種類
一致）時，才可以視為授權已釐清，不因此觸發強制「需人工確認」。

此規則不追溯強制重算已完成的分數，但下次查核任何一筆記錄時，必須依此規則重新檢查其
`recommendation_status` 是否需要修正——即使該筆的可信度分數維持不變。

## 通用原則

- 熱門度、實用度、可信度、可行度四項**分開**給分，不計算綜合總分。
- 每項分數必須有可追溯證據；證據不足時該項標示為 **未知（unknown）**，不得以 0 分代替。
- 每次評分需記錄：規則版本、輸入證據（連結／擷取內容摘要）、擷取時間、評分理由（1–3 句）。
- 實用度與可行度**必須附評估情境**（目標任務 + 目標環境），沒有具體情境時不得給分，只能記錄「情境未定義」。
- Repository 層級指標（stars/forks）不得直接當作單一 Skill 的分數；需說明推論鏈（例如：repo 僅一個 Skill 時方可視為該 Skill 的代理指標，並註明此為代理指標）。
- 沒有歷史快照時不計算成長率／趨勢；缺值一律標「未知」。

## 1. 熱門度（Popularity）

| 證據 | 說明 |
| --- | --- |
| Repository stars | GitHub API `stargazers_count` |
| Repository forks | GitHub API `forks_count` |
| 近期活動 | 最近 commit 時間、最近 30/90/180 天 commit 數 |
| 歷史變化 | 僅在有多次擷取快照時計算，否則標未知 |

評分帶（單一時間點證據，無歷史快照時的預設帶；有足夠歷史數據時可依成長率調整 ±10 分並在理由中說明）：

| Stars | 基準分 |
| --- | --- |
| 0–9 | 10 |
| 10–49 | 30 |
| 50–199 | 50 |
| 200–999 | 70 |
| 1000–4999 | 85 |
| ≥5000 | 95 |

近期活動調整：最近 90 天內有 commit → +5；超過 365 天無 commit → -15（下限 0）。

若無法取得 stars/forks（API 失敗或私有化）→ 標「未知」，不給 0 分。

## 2. 實用度（Utility）

必須先記錄**評估情境**：目標任務描述 + 預期輸出。無情境 → 標「情境未定義」，不給分。

| 檢查項 | 配分 |
| --- | --- |
| SKILL.md 是否清楚說明用途與適用情境 | 20 |
| 是否提供可執行的範例／使用步驟 | 20 |
| 功能是否覆蓋目標任務的關鍵需求（逐項核對） | 30 |
| 文件完整度（前提、限制、依賴皆有說明） | 15 |
| 實際使用回饋（issue、star 說明、外部評測等具體證據） | 15（無回饋證據則此項略過並於缺值原因註明「無回饋證據」，滿分改以其餘 85 分等比例換算） |

## 3. 可信度（Trustworthiness）

| 檢查項 | 配分 |
| --- | --- |
| 授權條款明確（LICENSE 存在且可辨識） | 20 |
| 來源可追溯（作者/組織資訊、非匿名鏡像） | 15 |
| 維護狀態（近 180 天內有活動或明確聲明穩定） | 20 |
| 內容與行為一致（SKILL.md 描述與實際腳本/指令相符） | 25 |
| 無可疑指令（無隱藏的憑證竊取、外傳、遠端執行等高風險模式） | 20（發現可疑指令 → 此項為 0 並在人工備註標記，整體不因此判死但需標示風險） |

靜態檢查結果僅代表「未發現明顯風險」，不得宣稱「已驗證安全」。

## 4. 可行度（Feasibility）

必須先記錄**目標環境**（如：Claude Code CLI、特定 OS、可用工具集）。無目標環境 → 標「情境未定義」，不給分；不得把通用相容性當作已驗證。

| 檢查項 | 配分 |
| --- | --- |
| 格式相容（`SKILL.md` 結構符合 Claude Code Skill 慣例） | 25 |
| 所需工具／指令在目標環境中可用或可安裝（逐項列出） | 30 |
| 依賴的外部服務／套件（列出未安裝項目，不得誤稱已安裝） | 25 |
| 設定成本（是否需要額外憑證、複雜設定） | 20（成本越低分越高） |

## 缺值與版本紀錄格式（每筆分數）

```json
{
  "aspect": "popularity|utility|trustworthiness|feasibility",
  "score": 0,
  "status": "scored|unknown|scenario_undefined",
  "rule_version": "scoring-rules@1.0.0",
  "evidence": ["..."],
  "captured_at": "ISO8601",
  "rationale": "..."
}
```
